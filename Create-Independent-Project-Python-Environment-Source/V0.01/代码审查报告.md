## 一、结论摘要

| 等级 | 数量 |
|------|------|
| 严重 | 0 |
| 高 | 3 |
| 中 | 6 |
| 低 | 4 |

**一句话结论**：V0.01 对系统是**干净的** —— 它只做三件事：建文件夹、调 `python -m venv`、弹窗提示。不碰注册表，不写 `%LOCALAPPDATA%`，不装任何后台程序，卸载就是删文件夹。**没有系统级风险。**

问题集中在两块：一是**换一台机器就跑不起来**（硬编码了 D 盘的 anaconda 和项目目录），二是**出错之后现场很脏**（失败不清理、界面假死、报错信息看不懂）。

## 二、高优先级问题

### H-1　创建失败会留下空文件夹，同名无法重试

**位置**：第 51–68 行

```python
    parent.mkdir(parents=True, exist_ok=True)
    dest.mkdir()                       # 52：文件夹已经建出来了

    python = resolve_python()          # 54：这里可能抛异常
    ...
    if result.returncode != 0:         # 64：venv 失败也直接抛
        raise ValueError(...)
```

**现象**：第 52 行先把项目文件夹建好，之后第 54 行找 Python、第 59 行建 venv，任何一步失败都直接 `raise`，**已建的 `dest` 不会被清理**。

**影响**：用户看到报错，解决问题后想用同一个名字重试，会撞上第 49 行的 "A folder with this name already exists"，只能自己去资源管理器手动删。对目标用户（Designer）来说这是个死结 —— 他不一定知道要去删那个空文件夹。

**建议**：把第 54 行之后的逻辑包进 `try/except`，失败时若 `dest` 是本次新建的且为空，`shutil.rmtree(dest)` 之后再把异常抛出去。

---

### H-2　`resolve_python()` 写死了本机专属路径，且优先级最高

**位置**：第 20–22 行

```python
    anaconda = Path(r"D:\Programs\anaconda\python.exe")
    if anaconda.is_file():
        return str(anaconda)
```

**现象**：这个硬编码路径排在 `shutil.which("python")`（第 24 行）**之前**，也就是说它压过了用户在 PATH 里的正常选择。

同类问题在第 11 行：

```python
DEFAULT_PARENT = Path(r"D:\vibecoding\cursor\CursorProjects")
```

**影响**：这是一个要当"绿色软件"分发的工具，却把开发者本机的目录结构烧进了代码。换台机器：没有 D 盘 → 默认保存位置直接不可用；有 D 盘但 anaconda 装在别处 → 这段逻辑白写；万一 `D:\Programs\anaconda\python.exe` 恰好是别的东西 → 用错解释器还查不出来。

**建议**：

- 本机路径降级成**可选兜底**，排在 `shutil.which` 之后，或者干脆删掉；
- `DEFAULT_PARENT` 改成通用默认（如 `Path.home() / "Projects"`），或读环境变量。

---

### H-3　子进程没有超时，整个界面全程假死

**位置**：第 59–63 行、第 89–93 行

```python
    result = subprocess.run(
        cmd,
        capture_output=True,
        text=True,
    )                                   # 没有 timeout
```

`create_project()` 是在 Tk 主线程上被 `on_create()`（第 89 行）同步调用的：

```python
        status_var.set("Creating an independent project environment. Please wait…")
        window.update_idletasks()       # 91：只刷了这一次
        path = create_project(...)      # 93：接下来完全阻塞
```

**影响**：

- `python -m venv` 通常要 10–60 秒。这段时间窗口不重绘，Windows 会把标题改成"未响应"并把窗口涂灰。第 90 行那句 "Please wait…" 用户大概率根本看不到，只看到程序卡死。
- 用户会以为卡了，反复点"Create project"（按钮没被禁用），或者直接叉掉窗口。
- 如果子进程真的卡住（网络盘、杀软拦截、venv 拉 pip 时卡网络），程序**永久挂死**，只能任务管理器杀掉。

**建议**：

- 给 `subprocess.run` 加 `timeout=180`，捕获 `subprocess.TimeoutExpired` 转成人话报错；
- 把 `create_project()` 丢到 `threading.Thread` 里跑，用 `window.after()` 回主线程更新状态；
- 创建期间禁用"Create project"按钮，防重复点击。

## 三、中等问题（健壮性）

### M-1　项目名校验不完整

**位置**：第 41–45 行

```python
    if any(ch in name for ch in FORBIDDEN):
```

只挡了 `\ / : * ? " < > |` 九个字符。没有挡住的：

| 输入 | 后果 |
|------|------|
| `CON`、`PRN`、`AUX`、`NUL`、`COM1`–`COM9`、`LPT1`–`LPT9` | Windows 保留设备名，`dest.mkdir()` 抛系统级错误，用户看到一串看不懂的英文 |
| 结尾带点，如 `abc.` | Windows 静默去掉尾点，实际建出来的文件夹名和用户输入的不一样 |
| ASCII 控制字符（0x00–0x1F） | 同样是系统级错误 |
| 超长名字 | `parent + name + \.venv\Scripts\python.exe` 很容易顶到 260 字符上限，venv 会在很深的地方失败 |

**建议**：抽一个 `validate_name()`，把上述四类一次性挡在前面，每类给一句明确的中文/英文提示。

### M-2　保存位置完全没有校验

**位置**：第 93 行

```python
            path = create_project(name_var.get(), Path(place_var.get()))
```

"Save in folder" 是一个可以随便打字的 `Entry`（第 115 行），内容直接被 `Path()` 包一下就用了。

- 留空 → `Path("")` 等价于 `.`，项目建到**当前工作目录**。对一个双击启动的 exe，cwd 可能是任意位置。
- 填相对路径 → 同上，位置不可预期。
- 第 51 行 `parent.mkdir(parents=True, exist_ok=True)` 会**沿途把不存在的目录全部建出来**。一个手滑的输入（比如少打一个盘符冒号）会在磁盘上凭空留下一串空目录。

**建议**：要求绝对路径；父目录不存在时明确提示"将新建 N 层目录，是否继续"；建之前检查可写权限。

### M-3　异常类型用得不对，导致 `warn_if_python_missing()` 很脆

**位置**：第 34、43、45、49、65 行全部 `raise ValueError`；第 128–135 行

"找不到 Python"、"名字为空"、"名字有非法字符"、"文件夹已存在"、"venv 建失败"，五类完全不同的错误共用 `ValueError`。而启动时的守卫只捕获 `ValueError`：

```python
def warn_if_python_missing() -> bool:
    if not getattr(sys, "frozen", False):
        return True
    try:
        resolve_python()
        return True
    except ValueError:                 # 135：只认 ValueError
```

**影响**：如果 `resolve_python()` 因为别的原因抛出（PATH 异常导致 `shutil.which` 抛 `OSError`、权限问题抛 `PermissionError`），**打包后的 exe 会在窗口出现之前直接静默退出** —— 用户双击没反应，什么都看不到，完全无从排查。

**建议**：定义一个自有异常（如 `class ProjectError(Exception)`）表示"要展示给用户的错误"；第 135 行改成 `except Exception`；在 `__main__` 最外层再加一个兜底 `try/except` + 错误弹窗。

### M-4　子进程输出解码没有容错

**位置**：第 61–62 行

```python
        capture_output=True,
        text=True,
```

`text=True` 用系统 locale 编码解码。中文 Windows 下是 cp936，但 venv 的输出在某些情况下是 UTF-8，一旦不匹配就抛 `UnicodeDecodeError` —— 而且这个异常恰恰发生在**读取失败原因**的时候，会把真正的错误完全盖掉。

**建议**：加 `encoding="utf-8", errors="replace"`，至少要有 `errors="replace"`。

### M-5　原始 stderr 未加工就丢进弹窗

**位置**：第 65–68 行 + 第 96 行

```python
        raise ValueError(
            "Could not create the project environment:\n"
            + (result.stderr or result.stdout or "Unknown error")
        )
```

venv 失败时的 traceback 可能几十行，原样塞进 `messagebox.showerror`，弹窗会撑出屏幕、"确定"按钮点不到。而且这些内容对目标用户（Designer）毫无意义。

**建议**：弹窗只显示一句人话 + "详细信息已写入日志文件"，完整输出另写文件。

### M-6　全程没有任何日志

整个文件没有一处日志输出。结合 M-3（exe 可能静默退出）和 H-3（可能挂死），一旦出问题**没有任何可追查的痕迹**。

**建议**：加最简单的文件日志，至少记录：最终选用的 Python 路径、完整的 venv 命令、返回码、stderr。

## 四、低优先级问题

### L-1　源码快照不完整：文档提到的 `_internal.bat` 不在这里

**位置**：第 1 行

```python
"""Started by hidden _internal.bat or the portable .exe: name a folder and create that project's Python environment."""
```

docstring 说这个程序是被一个隐藏的 `_internal.bat` 启动的，但**本文件夹里没有这个 `.bat`**，也没有任何打包说明（怎么从 `.py` 打成绿色 exe）。

`Source/README.md` 的承诺是「放入该版本**完整可读源码**」。按现在的内容，接手的人拿不到完整的构建链路，没法从源码复现出绿色版。

**建议**：把 `_internal.bat` 和打包命令（PyInstaller 参数 / `.spec`）一起补进本文件夹，或者在 `README.md` 里说明这一版为什么没有。

### L-2　禁用字符表硬编码了两遍

**位置**：第 10 行 vs 第 45 行

```python
FORBIDDEN = '\\/:*?"<>|'
...
        raise ValueError('Do not use these characters in the name: \\ / : * ? " < > |')
```

同一份内容写了两次，改一处忘另一处就会不一致。建议错误信息从 `FORBIDDEN` 拼出来。

### L-3　`windowsapps` 的排除方式偏脆

**位置**：第 27 行

```python
        if path.is_file() and "windowsapps" not in str(path).lower():
```

用路径里含不含 `windowsapps` 这个子串来判断是不是微软商店的假 python。思路对，但太依赖路径拼写。更可靠的做法是检查文件大小（商店占位符只有几百字节）或者实际跑一下 `python -c "import sys"` 看返回码。

同一段里第 30–32 行退到 `py.exe`，第 56–57 行加 `-3`，但 `py -3` 选的默认 3.x 仍可能是商店占位符，绕了一圈没解决问题。

**建议**：选定 Python 后，先跑一次 `python -c "import venv"` 验证可用，再拿去建 venv。

### L-4　"下一步怎么用"的提示偏弱

**位置**：第 99–106 行

```python
            "Later, run files with:\n"
            ".venv\\Scripts\\python.exe",
```

只给了一个路径片段。目标用户是 Designer，"用 `.venv\Scripts\python.exe` 跑文件"这句话对他而言不够可操作 —— 在哪儿输？怎么输？

这不是 bug，是产品层面的取舍。V0.02 已经在这个方向上做了改进（写 `.vscode/settings.json` + 双击开关）。这里只作记录，**V0.01 作为历史版本可以不改**。

## 五、建议的处理方式

V0.01 已经是历史版本，绿色包也已发出。所以先确认一件事：**这一版还要不要继续维护？**

- **如果只作为历史快照存档**：只需要补 L-1（把 `_internal.bat` 和打包说明补齐，让源码快照名副其实），其余不动。
- **如果还要继续发布 V0.01**：按 H-1 → H-2 → H-3 → M-3 → M-1/M-2 的顺序修。这五条修完，工具在别人机器上才算真的能跑、出错了也不留脏现场。

无论哪种，**都不用担心系统安全问题** —— V0.01 不碰注册表、不装常驻程序，这是它相对 V0.02 最大的优点。

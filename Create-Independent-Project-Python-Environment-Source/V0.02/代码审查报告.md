## 一、结论摘要

| 等级 | 数量 | 说明 |
|------|------|------|
| 严重（必须改） | 4 | 会实际改动用户系统状态且不可撤销，或行为与承诺不符 |

**最需要先知道的一句话**：V0.02 相比 V0.01 新增的"按项目开关双击 `.py`"这个功能，是**通过劫持全机 `.py` 文件关联**实现的；而且这个劫持**不受界面上那个复选框控制**，也**没有任何卸载入口**。

V0.01 是个干净的工具（只建文件夹和 `.venv`，不碰系统）。V0.02 引入的所有系统级风险，都来自下面 S-1 到 S-4 这四条。

## 二、严重问题

### S-1　复选框没勾也照样劫持全机 `.py` 双击（行为与承诺不符）

**位置**：`create_project.py` 第 193–196 行

```python
    write_project_helpers(dest, enabled)   # 193：只有这一行看了 enabled
    opener = ensure_opener()               # 194：无条件释放/编译开门程序
    wrap_double_click(opener)              # 195：无条件改注册表
    write_install_hook(opener)             # 196
```

**现象**：`enabled`（界面第 259–266 行那个勾）只传给了 `write_project_helpers()`，作用仅限于在项目文件夹里写/删一个 `use_project_env.on` 标记文件。第 194–196 行三个调用**完全没看 `enabled`**。用户只要点一次 "Create project"，全机 `.py` 的打开方式就被改掉了。

**影响**：

1. 与 `方案.md`「开关是按项目的，不是全电脑总开关」直接冲突。
2. 界面在没勾的时候还会弹窗告诉用户 "Double-click .py still uses the system Python."（第 236 行）—— 这是**假消息**。系统级关联其实已经被换成了开门程序，只是开门程序读到项目里没有标记文件，才把请求转发给 VS Code。表面现象一样，底层状态完全不同。
3. 用户在没有任何确认弹窗、事后也无从察觉的情况下，被写入了持久化的注册表项和一个 `%LOCALAPPDATA%` 下的可执行文件。这个行为模式和流氓软件一致，会同时被杀软和用户质疑。

**建议**（需要先跟产品需求确认走哪条）：

- **方案 A**：把第 194–196 行放进 `if enabled:` 里。改动最小，但缺点是用户事后双击项目里的「启用」`.bat` 时，全局开门程序可能还没装。
- **方案 B**：保留"全局开门程序装一次"的设计，但在**首次安装前弹确认框**，写清楚会改注册表的哪一项、怎么撤销；同时把第 234–239 行的提示文案改成实话。

### S-2　注册表劫持没有任何撤销 / 卸载路径

**位置**：`create_project.py` 第 100–123 行 `wrap_double_click()`

```python
            backup = winreg.CreateKey(
                winreg.HKEY_CURRENT_USER, rf"Software\IndependentPythonEnv\Backup\{progid}"
            )
            try:
                winreg.SetValueEx(backup, "open_command", 0, winreg.REG_SZ, str(current))
            finally:
                winreg.CloseKey(backup)
            winreg.SetValueEx(existing, None, 0, winreg.REG_SZ, command)
```

**现象**：原来的 open command 被备份到了 `HKCU\Software\IndependentPythonEnv\Backup\VSCode.py`，**但整个代码库里没有任何一处读取这个备份**。项目文件夹里那两个 `.bat`（`write_project_helpers()`，第 138–164 行）只会创建/删除项目内的标记文件，碰不到注册表。

**影响**：

- 用户删掉绿色 exe、删掉项目文件夹之后，注册表劫持依然在，`%LOCALAPPDATA%\IndependentPythonEnv\` 也依然在。**不可逆的系统污染**，跟"绿色软件"的定义直接矛盾。
- 更糟的场景：用户看到 `%LOCALAPPDATA%` 里有个不认识的 `OpenPyInProject.exe` 就手动删了 —— 此时注册表仍然指向这个不存在的 exe，**双击任何 `.py` 都直接失败、没有任何提示**。普通用户完全没法自救，也想不到是这个工具干的。

**建议**：

- 必须提供卸载入口：主界面加一个"恢复系统默认打开方式"按钮，或在 `%LOCALAPPDATA%` 目录里放一个 `卸载：恢复系统默认.bat`。逻辑是从备份键读回原值写回 ProgID，然后删掉备份键和 `%LOCALAPPDATA%` 目录。
- 开门程序自身也要有兜底，见 S-4。

### S-3　运行时用 PowerShell 编译磁盘上的 C# 源码 → 本地代码执行 / 持久化通道

**位置**：`create_project.py` 第 60–80 行 `compile_opener()`

```python
    src = tool_dir() / "open_py_in_project.cs"
    ...
    result = subprocess.run(
        ["powershell", "-NoProfile", "-ExecutionPolicy", "Bypass", "-Command", ps],
        capture_output=True,
        text=True,
    )
```

**现象**：程序把同目录下的 `open_py_in_project.cs` 读进来，用 `-ExecutionPolicy Bypass` 调 PowerShell 的 `Add-Type` 现场编译成 exe，写进 `%LOCALAPPDATA%`，然后（S-1）注册成全机 `.py` 的处理程序。

**影响**：

1. **攻击面**：非打包运行时 `tool_dir()`（第 29–32 行）返回的就是脚本所在目录。任何能往这个目录写文件的进程 —— 包括用户自己把别处下载的文件解压到同一个文件夹 —— 都可以替换掉那个 `.cs`。结果是**任意代码被编译出来，并被注册成"以后每次双击 `.py` 都会执行"的程序**。这是一个现成的持久化通道。
2. **合规与观感**：`-ExecutionPolicy Bypass` + 运行时编译 + 写 `%LOCALAPPDATA%` + 改注册表，这四件事凑在一起是行为检测的典型命中组合。生成的 exe 无数字签名，SmartScreen 也会拦。
3. **可用性**：依赖 PowerShell 和 .NET Framework 编译器可用。在受控语言模式（Constrained Language Mode）、AppLocker 策略、或者 PowerShell 被移除/替换的机器上会直接失败。
4. 第 72–76 行的 `subprocess.run` **没有 `timeout`**，编译卡住会永久挂死整个界面（见 H-6）。

**建议**：

- **最优解：不要在运行时编译**。把 `OpenPyInProject.exe` 作为构建产物预先编译好、随绿色包一起分发。`ensure_opener()` 第 90–93 行已经支持这条路径了，把 `compile_opener()` 整个删掉即可。
- 如果一定要保留运行时编译作为兜底：校验 `.cs` 的哈希；只从 `sys._MEIPASS`（打包内部）读取而不从脚本目录读；加 `timeout`。

### S-4　劫持了 `.py` 关联，却在找不到 VS Code 时让文件彻底打不开

**位置**：`open_py_in_project.cs` 第 40–45 行、第 92–111 行

```csharp
        string codeExe = FindCodeExe();
        if (codeExe == null)
        {
            MessageBox.Show("VS Code was not found.", "Open with project environment");
            return;                       // ← 直接放弃，文件根本没被打开
        }
```

`FindCodeExe()` 只查三个**硬编码**路径：

```csharp
            @"D:\Programs\Microsoft VS Code\Code.exe",
            Path.Combine(LocalApplicationData, @"Programs\Microsoft VS Code\Code.exe"),
            @"C:\Program Files\Microsoft VS Code\Code.exe"
```

**现象**：一旦 S-1 的劫持生效，这个 exe 就成了全机 `.py` 的唯一入口。而它认 VS Code 只靠三个写死的路径。装在 `E:\` 盘、装的是 VSCodium、装的是 Insiders 版、或者在 `C:\Program Files (x86)\` —— 全都找不到。第 96 行那个 `D:\Programs\Microsoft VS Code\Code.exe` 更是开发者本机专属路径，不该出现在要分发的软件里。

**影响**：用户双击任何 `.py`，只会看到一个 "VS Code was not found." 的框，文件打不开，而且**完全看不出是被谁劫持的**。等于把一个原本可用的系统功能改成了不可用。

**建议**：

- `FindCodeExe()` 增加：读注册表 `HKCU`/`HKLM` 的 `...\App Paths\Code.exe`；查 `PATH` 里的 `code.cmd`；用 `%ProgramFiles%` / `%ProgramFiles(x86)%` 环境变量而不是写死 `C:\`。
- **更关键的是兜底**：找不到 VS Code 时不要弹框结束，而应该读 `HKCU\Software\IndependentPythonEnv\Backup\VSCode.py` 里备份的原始命令去执行，或者退化成 `ShellExecute` 用系统默认方式打开。**绝不能出现"文件打不开"这个终态。**

## 三、高优先级问题

### H-1　创建失败会留下空文件夹，且同名无法重试

**位置**：`create_project.py` 第 178–191 行

```python
    parent.mkdir(parents=True, exist_ok=True)
    dest.mkdir()                       # 179：文件夹已经建出来了
    python = resolve_python()          # 181：可能抛异常
    ...
    if result.returncode != 0:         # 187：venv 失败也直接抛
```

失败时 `dest` 不会被清理。用户解决问题后想用同一个名字重试，会撞上第 175 行的 "A folder with this name already exists"，只能自己去资源管理器手动删。对目标用户（Designer）来说是个死结。

**建议**：`try/except` 包住第 181 行之后的逻辑，失败时若 `dest` 是本次新建且为空则 `shutil.rmtree(dest)`，再抛出异常。

### H-2　`resolve_python()` 写死本机专属路径且优先级最高

**位置**：`create_project.py` 第 40–42 行

```python
    anaconda = Path(r"D:\Programs\anaconda\python.exe")
    if anaconda.is_file():
        return str(anaconda)
```

排在 `shutil.which("python")`（第 44 行）之前，压过了用户 PATH 里的正常选择。同类问题在第 13 行：`DEFAULT_PARENT = Path(r"D:\vibecoding\cursor\CursorProjects")`，在没有 D 盘的机器上默认保存位置直接不可用。

**建议**：本机路径降级为可选兜底、排在 `which` 之后或直接删掉；`DEFAULT_PARENT` 改成通用默认（如 `Path.home() / "Projects"`）。

### H-3　`ensure_opener()` 每次都覆盖 exe，被占用时整个流程崩在最后一步

**位置**：`create_project.py` 第 87–97 行

```python
    bundled = tool_dir() / OPENER_NAME
    if bundled.is_file():
        shutil.copy2(bundled, dest)    # 92：无条件覆盖
        return dest
```

如果此刻 `OpenPyInProject.exe` 正在运行（用户刚双击过某个 `.py`），Windows 会锁住这个文件，`copy2` 抛 `PermissionError`。这个调用发生在第 194 行，也就是 **`.venv` 已经建好之后**。用户看到 "Did not succeed."，但项目其实已经建了一大半 —— 报错和实际状态不符。

**建议**：先比对哈希或修改时间，一致就跳过复制；复制失败时降级为警告而不是让整个 `create_project()` 失败（主要产物 `.venv` 已经成功了）。

### H-4　`APPDATA_DIR` 在环境变量缺失时会退化成相对路径

**位置**：`create_project.py` 第 19 行

```python
APPDATA_DIR = Path(os.environ.get("LOCALAPPDATA", "")) / "IndependentPythonEnv"
```

取不到 `LOCALAPPDATA` 时，结果是相对路径 `IndependentPythonEnv`，第 88 行的 `mkdir` 会在**当前工作目录**下建文件夹。对一个双击启动的 exe，cwd 可能是任意位置。属于静默的错误行为，不报错但结果全错。

**建议**：取不到就直接抛错退出，或用 `os.path.expanduser("~")` 兜底。

### H-5　`write_install_hook()` 在中文用户名的机器上必崩

**位置**：`create_project.py` 第 126–135 行

```python
    cmd.write_text(
        "@echo off\r\n"
        f'if exist "{opener}" (\r\n'    # opener 是 C:\Users\<用户名>\AppData\Local\...
        ...
        encoding="ascii",              # 133：写死 ascii
        newline="",
    )
```

Windows 中文用户名极其常见。一旦用户名里有中文，`encoding="ascii"` 直接抛 `UnicodeEncodeError`。而且和 H-3 一样，这发生在第 196 行 —— **`.venv` 已经建好之后**。

**建议**：这个函数本身是死代码（见 L-1），建议**连同第 196 行的调用一起删掉**，一次解决两个问题。若要保留，编码改成 `utf-8` 或 `gbk`。

### H-6　所有子进程调用都没有超时，界面全程假死

**位置**：`create_project.py` 第 72–76 行（PowerShell 编译）、第 186 行（建 venv）

```python
    result = subprocess.run(cmd, capture_output=True, text=True)   # 无 timeout
```

`create_project()` 跑在 Tk 主线程上，由 `on_create()`（第 218–227 行）同步调用：

```python
        status_var.set("Creating an independent project environment. Please wait…")
        window.update_idletasks()      # 220：只刷了这一次
        path = create_project(...)     # 222：接下来完全阻塞
```

**影响**：`python -m venv` 通常 10–60 秒，PowerShell 编译再加几秒。这段时间窗口不重绘，Windows 会显示"未响应"并把窗口涂灰，第 219 行那句 "Please wait…" 用户多半看不到。按钮也没禁用，用户会重复点击。子进程真卡住时程序永久挂死，只能任务管理器杀。

**建议**：给每个 `subprocess.run` 加 `timeout=`（venv 建议 180 秒，PowerShell 编译 120 秒）并捕获 `TimeoutExpired`；把 `create_project()` 放进 `threading.Thread`，用 `window.after()` 回主线程更新状态；创建期间禁用按钮。

### H-7　`FindProjectFolder` 无限向上找 `.venv`，可能把一整个大目录当成项目

**位置**：`open_py_in_project.cs` 第 69–90 行

```csharp
        while (!string.IsNullOrEmpty(folder))
        {
            string venvPy = Path.Combine(folder, ".venv", "Scripts", "python.exe");
            if (File.Exists(venvPy)) { return folder; }
            DirectoryInfo parent = Directory.GetParent(folder);
            ...
```

一路往上走到盘符根目录为止，没有层数限制。只要某个上层目录（比如 `D:\vibecoding`，甚至盘根）里存在一个 `.venv`，它下面**所有** `.py` 都会被判定属于那个"项目"，然后第 52 行用 `-n` 把那个巨大的文件夹整个用 VS Code 打开。

**建议**：限制向上查找层数（比如最多 5 层）；或者要求该目录**同时**存在 `use_project_env.on` 标记才认（现在是先找到 `.venv` 目录、再在那个目录里找标记，顺序上没问题，但找 `.venv` 这一步本身不设限）。

## 四、中等问题（健壮性）

### M-1　项目名校验不完整

**位置**：`create_project.py` 第 168–172 行

只挡了 `\ / : * ? " < > |` 九个字符。没挡住的：

| 输入 | 后果 |
|------|------|
| `CON`、`PRN`、`AUX`、`NUL`、`COM1`–`COM9`、`LPT1`–`LPT9` | Windows 保留设备名，`mkdir` 抛系统级错误，用户看到看不懂的英文 |
| 结尾带点，如 `abc.` | Windows 静默去尾点，实际文件夹名和输入不一致 |
| ASCII 控制字符（0x00–0x1F） | 同样是系统级错误 |
| 超长名字 | `parent + name + \.venv\Scripts\...` 容易顶到 260 字符上限 |

**建议**：抽一个 `validate_name()` 统一拦截，每类给一句明确提示。

### M-2　保存位置完全没有校验

**位置**：`create_project.py` 第 222 行

```python
            path = create_project(name_var.get(), Path(place_var.get()), enabled_var.get())
```

"Save in folder" 是可以随便打字的 `Entry`（第 256 行）。留空 → `Path("")` 等价于 `.`，项目建到不可预期的 cwd；填相对路径同理。而且第 178 行 `parent.mkdir(parents=True, exist_ok=True)` 会**沿途把不存在的目录全建出来** —— 一个手滑的输入会在磁盘上留下一串空目录。

**建议**：要求绝对路径；父目录不存在时明确提示"将新建 N 层目录，是否继续"；建之前检查可写权限。

### M-3　异常类型用得不对，`warn_if_python_missing()` 因此很脆

**位置**：`create_project.py` 第 54、63、78、170、172、175、188 行全部 `raise ValueError`；第 278–297 行

"找不到 Python"、"缺少 `.cs` 文件"、"PowerShell 编译失败"、"名字为空"、"文件夹已存在"、"venv 失败" —— 六类完全不同的错误共用 `ValueError`。而启动守卫只捕获 `ValueError`：

```python
    try:
        resolve_python()
        return True
    except ValueError:                 # 285
```

**影响**：如果 `resolve_python()` 因为别的原因抛出（`shutil.which` 遇到异常 PATH 抛 `OSError`、权限问题抛 `PermissionError`），**打包后的 exe 会在窗口出现之前静默退出** —— 用户双击没反应，完全无从排查。

**建议**：定义自有异常（如 `class ProjectError(Exception)`）表示"要展示给用户的错误"；第 285 行改成 `except Exception`；`__main__` 最外层加兜底 `try/except` + 错误弹窗。

### M-4　子进程输出解码没有容错

**位置**：`create_project.py` 第 74–75 行、第 186 行

`capture_output=True, text=True` 用系统 locale 编码。中文 Windows 下是 cp936，但 PowerShell 在某些配置下输出 UTF-8/UTF-16，一旦不匹配就抛 `UnicodeDecodeError` —— 而且恰恰发生在**读取失败原因**的时候，会把真正的错误完全盖掉。

**建议**：加 `encoding="utf-8", errors="replace"`，至少要有 `errors="replace"`。

### M-5　原始 stderr 未截断就丢进 MessageBox

**位置**：`create_project.py` 第 77–80 行、第 188–191 行、第 225 行

```python
            "Could not create the project environment:\n"
            + (result.stderr or result.stdout or "Unknown error")
```

venv 失败的 traceback 可能几十行；PowerShell 编译失败会输出整段编译器诊断。全部原样塞进 `messagebox.showerror`，弹窗可能撑出屏幕、按钮点不到。而且这些内容对目标用户毫无意义。

**建议**：弹窗只显示一句人话 + "详细信息已写入日志"，完整输出写到 `%LOCALAPPDATA%\IndependentPythonEnv\last_error.log`。

### M-6　全程没有任何日志

整个 V0.02 没有一处日志输出。结合 S-1（注册表可能静默 no-op，见 M-7）、H-3、M-3，出问题时**没有任何可追查的痕迹** —— 而这一版是会改系统状态的，更需要审计记录。

**建议**：加 `logging.FileHandler` 写到 `%LOCALAPPDATA%\IndependentPythonEnv\app.log`，至少记录：选用的 Python 路径、venv 命令与返回码、注册表改动前后的值、开门程序来自哪里（bundled 还是现场编译）。

### M-7　注册表劫持在 ProgID 不匹配时静默失效

**位置**：`create_project.py` 第 102–109 行

```python
    for progid in ("VSCode.py",):
        command_key = rf"Software\Classes\{progid}\shell\open\command"
        try:
            existing = winreg.OpenKey(...)
        except FileNotFoundError:
            continue                   # 键不存在，什么都不做，也不告诉任何人
```

只处理 `VSCode.py` 这一个 ProgID。但实际决定双击行为的是 `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\FileExts\.py\UserChoice`，它可能指向 `Python.File`、`py_auto_file` 或别的编辑器的 ProgID。这些情况下这段代码**什么都不做也不报错**，用户以为功能生效了，实际没有。

另外第 105 行 `winreg.OpenKey(..., KEY_READ | KEY_SET_VALUE)` 只捕获了 `FileNotFoundError`，权限错误（`PermissionError`）会直接穿透上去变成一个看不懂的报错。

**建议**：先读 `UserChoice\ProgId` 拿到真正生效的 ProgID 再改；改不了时给用户明确提示（"你的 .py 目前由 XXX 打开，本功能暂不支持"），而不是静默通过。

### M-8　`.vscode/settings.json` 里两条设置互相打架，且被无条件覆盖

**位置**：`create_project.py` 第 21–26 行、第 139–141 行

```json
  "python.terminal.executeInFileDir": true,
  "terminal.integrated.cwd": "${workspaceFolder}"
```

前者让运行时的工作目录是"文件所在目录"，后者让终端 cwd 是"工作区根目录"，语义相反，需要确认到底想要哪个行为。

另外第 141 行 `write_text` 是**无条件覆盖**。当前调用链里 `dest` 一定是刚建的新文件夹所以撞不上，但 `write_project_helpers(dest, enabled)` 从签名上看是可复用的 —— 一旦以后拿它处理已有项目，会直接抹掉用户自己的 `settings.json`。

**建议**：确认这两条设置的取舍；`settings.json` 已存在时改成合并而不是覆盖。

### M-9　`.vscode/settings.json` 并不能真正"钉死"解释器

`方案.md` 写的是「`.vscode/settings.json`（钉死本文件夹用 `.venv`）」。实际上 `python.defaultInterpreterPath` 只是**默认值** —— VS Code 一旦在该工作区里存过一次 interpreter 选择（存在 workspace state 里），这条设置就不再生效。文档承诺的强度高于实现。

**建议**：要么改文档措辞，要么在 `README` 里明确写"如果 VS Code 右下角显示的不是 `.venv`，请手动选一次"。

## 五、低优先级问题（冗余 / 死代码 / 风格）

### L-1　`write_install_hook()` 是纯死代码

**位置**：`create_project.py` 第 126–135 行

一个**只包含注释的 `if` 块** —— 执行它不产生任何效果。而且这个文件生成之后，代码里也没有任何地方会去调用它。纯垃圾文件，还顺带引入了 H-5 那个崩溃。

字符串里没有任何占位符，`f` 前缀多余。（采纳 L-1 的话这条自动消失。）

**位置**：`create_project.py` 第 102 行


单元素元组上的循环，是一层没有实际用途的抽象。要么按 M-7 的建议改成真的处理多个 ProgID，要么摊平成一次直接调用。

### L-4　`_ps_quote()` 定义在使用它的函数之后

**位置**：第 66、70 行使用，第 83 行定义

### L-5　禁用字符表硬编码了两遍

**位置**：`create_project.py` 第 12 行 vs 第 172 行

```python
FORBIDDEN = '\\/:*?"<>|'
...
        raise ValueError('Do not use these characters in the name: \\ / : * ? " < > |')
```

同一份内容写两次，改一处忘另一处就不一致。建议错误信息从 `FORBIDDEN` 拼出来。

### L-6　`open_py_in_project.cs` 的若干小问题

- **第 52 行**：启用时永远带 `-n`（新窗口），双击多次会堆出一大串 VS Code 窗口。建议去掉 `-n`，或只在该项目尚未打开时才用。
- **第 47–57 行**：`psi.Arguments` 靠字符串拼接手工加引号。.NET Framework 没有 `ArgumentList`，但至少要处理路径末尾反斜杠的转义边界。
- **第 20–35 行**：全程没有校验 `args[0]` 是不是 `.py`。任何文件被拖到这个 exe 上都会被当作 Python 文件处理。
- **第 7–11 行**：只有 `AssemblyFileVersion`，缺 `AssemblyVersion`；`Main` 永远返回 0，调用方无法判断成败。

### L-7　源码快照不完整：缺少构建产物和打包说明

`ensure_opener()` 第 90 行期望在打包内部找到一个现成的 `OpenPyInProject.exe`，但本文件夹里既没有这个 exe，也没有把 `.py` 打成绿色 exe 的打包命令（PyInstaller 参数 / `.spec` 文件）。

`Source/README.md` 的承诺是「放入该版本**完整可读源码**」。按现在的内容，接手的人拿不到完整构建链路，没法从源码复现出绿色版。

**建议**：补上打包脚本或 `.spec`，并在 `V0.02/README.md` 里写清楚 `.cs` 是预编译还是现场编译（这直接关系到 S-3 的取舍）。
